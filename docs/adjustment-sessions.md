# Adjustment Session (Super Adjustment only)

Built 2026-10-21. For a physical count of one Project / Warehouse (godown) that takes several days and several Super Adjustments. Normal Adjustments are not touched.

## How it works
1. **Start** (`start-adjustment-sessions`): Super Adjustments > Adjustment Sessions > Start. One open session per Project / Warehouse (unique `open_warehouse_id`, so it holds under a race). Reference `ASN-0001`.
2. While it is **open**, every Super Adjustment made for that warehouse is linked to it (`super_adjustments.adjustment_session_id`, set in `SuperAdjustmentController::persist`; an older count is linked on edit only if it was made after the session started). On the form the "items not in this count" question is switched off for that warehouse (`uncountedItems` answers `[]`) and a banner says the count belongs to the session. With no open session the question works exactly as before.
3. An item is **counted** once it is on a Draft, Awaiting or Approved Super Adjustment of the session (a Rejected one does not count). **Not counted** = items with stock in the warehouse on no such document, live on the session page, with a "moved since start" flag when the stock row changed after the session started.
4. **End** (`end-adjustment-sessions`): refused while a document of the session waits for approval. The dialog lists the uncounted items with tick boxes (all ticked except the ones that moved). Ticked items are cleared by ONE normal Super Adjustment (counted at zero, `auto_cleared`), created through `SuperAdjustmentController::submitCount`, so the usual one / two Super Admin approvals still apply (clearing needs `create-super-adjustments` too). Unticked items stay as they are. Ending without ticking anything is allowed. The result (counted / cleared / kept) is kept in `adjustment_sessions.snapshot`.

- `php artisan adjustments:session-samples` adds two review samples to the LOCAL database (an OPEN session with an approved and a waiting count, and an ENDED session with two approved counts and the clearing count waiting for approval); every one says SAMPLE; counts equal the stock, so no stock moves and nothing is sent. `--remove` takes them away.

The column is now a nullable plain timestamp (migrations `2026_12_03_100000` and `2026_12_03_100100`); `adj_session_test` checks it.

## Stop Stock Movement (optional, 2026-10-21)
A session can also **halt the stock movement of its Project / Warehouse** while the count goes on, so counted items cannot move before their count is approved. It is a tick box when the session is started, and a **Stop stock movement / Release stock movement** button on the session page while it is open.

- **Who:** permission `stop-stock-movement` (Super Admin by default, give it to a role on the Roles screen) AND the person's own password, asked every time, even for a Super Admin. A wrong password is refused, logged and counted by the security alert.
- **What is held:** both directions (into and out of the warehouse), for everybody including a Super Admin: Check-ins, Check-outs, Transfers (create, edit, delete, restore, approve, receive, bulk receive, cleanup), Multi Transfers (create, approve), Reallocations (source AND every destination, all steps), Issue Material and Return Material, normal Adjustments. The Super Adjustments of the count itself (and the approval that changes the stock, and the clearing count) are never held. External Stock keeps its own ledger and is not held. Material Requests are paperwork (draft transfers are made, nothing moves until a transfer is finalised, and that is held).
- **How it shows:** `StockHalt` (app/Support) reads the open halted sessions and every page gets `stockHalts` (warehouse id => who, when, session, full sentence). The warehouse pickers of the movement forms carry the `stock-move` flag: a halted warehouse stays in the list but is locked, red, with "Stock movement halted · NAME"; clicking it does not select it and a popup names the person; one that is already chosen (for example the person's current warehouse) shows the same sentence under the field. The Return form and the Reallocation destination list show it too. The server is the real guard (`GuardsCompletedWarehouse::rejectIfWarehouseBlocked`, next to the existing "completed project" check), so an old page, an import or another tab is refused with the same sentence: "Stock movement for W has been halted by NAME on DATE because of the physical count in Adjustment Session ASN-0001...".
- **Lifetime:** lifted by the Release button (stays open, `halt_released_by/at` kept), by ending the session (released by the person who ends it), never survives the session. It can be halted again while open. Stored on the session (`halt_stock`, `halted_by_user_id`, `halted_at`, `halt_released_by_user_id`, `halt_released_at`, migration `2026_12_05_100000`), shown on the session page, list, print / PDF and the activity log; Adjustments workflow events `stock_halted` / `stock_released`.
- **Tests:** `ver/stock_halt_test.php` (58 checks: permission, password, every movement type refused with a working control on another warehouse, reallocation destination, count still works, release, end, per-warehouse).

## Review for first real use (2026-10-22)
- **Report of a session** (screen, Print, PDF): every Super Adjustment of the session with who made it and when, who approved or rejected it and when, how many items; the **untouched items** with their **stock in the warehouse** and its value (total value left untouched); and a **History** (who started the session, halted / released stock movement, made / approved / rejected / deleted each count, who ended it, with date and time, oldest first). The history is built from the activity log plus the session and the Super Adjustment records, including deleted ones, so it keeps working for sessions that were started before.
- Each Super Adjustment in the table opens **in a new tab** (the reference link, and a click on the row).
- A session only ever links **Super Adjustments** (the link column exists on `super_adjustments` only; normal Adjustments are unaffected). There is no route that deletes a session: its record stays.
- Halting stock movement stays optional (leave it off while counting manually).
- Phones: the tables turn into cards (name above time, long labels shortened); tablets: the two tables on the session page fit without sideways scrolling (the Sessions list scrolls inside its own box, like the other lists).
- Test: `ver/session_review_test.php` (35 checks) on top of `adj_session_test` (62) and `stock_halt_test` (58).
